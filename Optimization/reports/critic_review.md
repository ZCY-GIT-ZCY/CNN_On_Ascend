## 2. 总体评价

从材料完整性看，这组实验并不是“没有数据支持”的报告：主表中的大多数性能数字、图统计数字和严格复测数字都能在结果文件中找到对应来源。因此，这不是一份随意拼接的报告，而是一份已经进行了较多测量与汇总的实验材料。

但从更严格的实验科学性与审稿标准看，当前工作仍然存在几个关键问题：

1. **实验设计中的对照关系不够干净**，导致“优化是否有效”与“导出链路是否不同”混在一起。
2. **数值正确性没有被作为性能比较的前置门槛**，导致部分已经数值异常或未完成验证的变体，仍被纳入性能结论。
3. **测试环境存在显著波动与干扰痕迹**，使得极小幅度性能差异难以被严肃解释。
4. **报告整体数字大多对齐，但结论表达强度高于数据本身的证据强度**。

换言之：当前材料足以支持“工程观察”，但还不足以支撑某些更强的因果性结论。

## 3. 实验设计上的不科学之处

### 3.1 基线定义不对等，削弱了“优化有效性”结论

当前 `baseline_copy` 不是“同一上游模型、同一导出路径、只差一个优化开关”的对照基线，而是项目中原有的、已部署的 AIPP OM。

这意味着实验实际上在比较两类对象：

- 一类是成熟部署产物；
- 另一类是基于 `torchvision` 权重重新导出、重新编译得到的优化变体。

这种设计适合回答：

- “当前工程里谁跑得最快？”

但不适合严格回答：

- “某种前端优化本身是否带来了收益？”

因为这里同时混入了多个变量：

- 上游模型来源差异；
- 导出链路差异；
- 编译产物形成路径差异；
- 潜在图表达与参数组织差异。

因此，“所有优化都没超过基线”可以作为工程现象成立；但若进一步上升为“这些优化方法本身无效”，证据并不纯净。

### 3.2 缺少真正的“重新导出普通版”对照组

从审稿角度看，当前实验最缺的不是更多优化，而是一个真正的中性对照组，例如：

- 同样从 `torchvision` 重新导出；
- 同样走相同的编译流程；
- 但不启用 `shape_inferred`、`fp16`、`onnxsim`、`onnxoptimizer`、`channels_last`、`bn_folded` 等额外优化。

如果没有这样一个 `reexport_plain` 类似的对照，那么当前实验实际上只能说明：

- “重新导出后的这些变体整体不如现有部署 OM。”

却不能清楚区分：

1. 是优化方法本身有害；
2. 还是重新导出链路整体就比现有部署链路差。

这是当前设计里最核心的科学性缺陷。

### 3.3 多个优化并非严格单变量实验

虽然实验名称看起来像在做逐项因素隔离，但从结果表现看，很多变体并不一定只改变了单一因素。

例如：

- `fp16` 不仅改变权重精度，也可能改变图中某些算子的表达和后端 kernel 选择；
- `channels_last` 理论上想测试 layout 痕迹，但最终图统计几乎不变，说明它未必只改变了一个清晰可解释的变量；
- `bn_folded` 在 ResNet50 上不仅图结构收缩，还伴随严重数值异常，这已超出“纯融合收益”讨论范畴。

因此，这组实验更像“工程变体测试”，而不是严格意义上的单因素实验。若在报告中使用很强的因果语言，会显得结论先于证据。

### 3.4 数值正确性未被设为性能比较的前置条件

这是一个很严重的方法学问题。

合理的实验顺序应该是：

1. 先验证变体数值正确；
2. 数值通过后，再谈性能优劣。

但当前材料中存在这样的情况：

- `resnet50 bn_folded` 数值明显错误；
- `resnet50 fp16` 数值验证失败；
- 但它们仍被纳入性能排名与结论叙事。

这会让性能分析掺入“无效模型”或“未验证模型”，从而削弱整组结论的可信度。

### 3.5 极小幅度差异缺乏足够统计支撑

报告中重点讨论了 strict suite 下的微弱差异：

- MobileNetV3-Small `fp16` 相对 baseline 约 `-0.014%`；
- ResNet50 `fp16` 相对 baseline 约 `-0.336%`。

但这类差异量级远小于测试中可见的多轮波动与尾部抖动，因此很难被视为“已被严肃确认的性能优势”。

更稳妥的解释应当是：

- `fp16` 在严格复测中表现出“接近基线”甚至“局部略优”的趋势；
- 但当前样本量、波动水平和环境控制力度不足以支撑“稳定优势成立”。

## 4. 实验实施过程中的干扰与污染风险

### 4.1 单模型严格长跑结果明显失稳

从单模型严格 benchmark 文件看，运行状态存在明显异常。

#### MobileNet baseline 单模型严格测试

- round1: `1.0997 ms`
- round2: `1.0649 ms`
- round3: `3.6591 ms`

第三轮延迟突然升高到前两轮的约 3 倍，说明单模型长跑过程中存在显著状态漂移。

#### MobileNet fp16 单模型严格测试

- round1: `4.4276 ms`
- round2: `4.3825 ms`
- round3: `1.8295 ms`

这里则出现完全反向的异常：前两轮非常慢，第三轮明显下降。说明长跑过程中的不稳定性不是偶然一次尖峰，而是系统性问题。

#### ResNet fp16 单模型严格测试

- `max_ms` 多次达到 `10 ms` 以上；
- 各轮 `std_ms` 高达 `1.226 / 1.153 / 0.766`。

这类波动远超一般“轻微噪声”范畴，更像存在强干扰或运行状态异常。

因此，当前单模型 strict benchmark 更像在提醒：

- 实验环境还没有被控制到足以支撑细粒度性能结论。

### 4.2 strict suite 虽然更好，但并不等于完全干净

strict suite 的交错运行设计确实比单跑更可信，但结果中仍然能看到明显异常尾部：

- `mobilenet_baseline_run1` 某轮 `max_ms = 2.432 ms`；
- `resnet_baseline_run1` 某轮 `max_ms = 4.650 ms`；
- `resnet_fp16_run2` 某轮 `std_ms` 显著偏高。

这说明 strict suite 至多证明：

- 它比单模型长跑更稳；

而不能证明：

- 它已经充分排除了温度、调度、资源争用和运行顺序的影响。

### 4.3 交错顺序仍可能存在偏差

当前 strict suite schedule 为：

- baseline1 → fp16_1 → fp16_2 → baseline2

这并非最均衡的随机化/交错方案，而是 `A-B-B-A`。对于非常小的差异，这种顺序仍可能引入偏差，因为：

- 中间两次连续运行同一种变体，可能共享相似状态；
- 首尾两次 baseline 可能受到时间漂移的边界效应影响。

如果要严肃讨论千分之几甚至万分之几的差异，这种顺序设计仍显得不够硬。

### 4.4 cooldown 有帮助，但目前看不出是否足够

配置中已经加入：

- round 间 cooldown；
- model 间 cooldown。

这说明实验者已经意识到热状态和顺序效应问题，这是积极的。

但从结果看，单模型 strict 依旧严重失稳，说明 cooldown 是否足够并没有被结果证明。换言之，cooldown 的存在不能直接等价于“干扰已被控制”。

## 5. 数据正确性问题

### 5.1 `resnet50 bn_folded` 数值已经失真，不应被当作有效性能样本

这是当前数据中最严重的问题。

数值验证结果显示，`resnet50 bn_folded`：

- `max_abs_diff = 655290112.0`
- `mean_abs_diff = 133927504.0`
- `rmse = 168968768.0`
- `cosine_similarity_mean = -0.0994`
- `top1_match_rate = 0.0`

这不是“小误差”或“精度略降”，而是明显的数值错误，说明该变体很可能已经失去与原模型等价的语义。

在这种情况下，将它继续作为“有效候选”纳入性能排名，并用它支撑“节点数减少但性能变慢”的因果论证，是不严谨的。它慢，不一定是因为“前端图更简洁不代表更快”，也可能只是因为模型本身已经坏了。

因此，这个样本应被视为：

- 一个失败变体；
- 一个实现或导出过程可能存在问题的异常案例；

而不是普通的性能较差候选。

### 5.2 `resnet50 fp16` 未完成数值验证，但被赋予了较强结论地位

`resnet50 fp16` 在数值验证结果中的状态是 `failed`，原因是 ONNXRuntime CPUExecutionProvider 不支持相关算子版本/域。

这意味着：

- 当前并没有证据证明它在数值上等价于原模型；
- 只能说“数值验证尚未完成”，而不是“验证通过”。

但报告却多次将它作为：

- 最接近基线的候选；
- strict suite 中略优的方向；
- 唯一值得继续跟踪的方向之一。

这会造成一个闭环缺口：

- 你有性能迹象；
- 但没有正确性闭环；
- 因此还不能把它当成“可信候选最优方案”来叙述。

### 5.3 模型大小的统计口径存在混杂

当前材料中“模型大小”至少出现了两种口径：

- ONNX 文件大小；
- OM / runtime artifact 对应大小。

例如：

- 报告第 5 节中提到的 `97.41 MB`、`48.72 MB`、`9.71 MB`、`4.88 MB`，明显是 ONNX 文件大小；
- `experiment_results.json` 中 `baseline_copy` 的 `model_size_mb` 又更像 OM 文件大小。

如果报告不持续、明确地区分这两类口径，读者就容易误以为所有表格都在比较同一种对象，从而造成理解偏差。

### 5.4 `shape_inferred` 与 `onnx_shape_inferred` 命名共存，容易混淆阶段

结果文件中同时出现：

- `onnx_shape_inferred`（graph 阶段）
- `shape_inferred`（runtime 阶段）

这未必是错误，但从数据管理规范性上看，这种命名方式容易让阅读者或后续脚本误把图阶段结果和运行阶段结果混为一谈。当前报告还能勉强辨认其语义，但这一命名方式不够稳健。

## 6. 报告与实验数据的对齐情况

### 6.1 对齐较好的部分

当前报告并非“数字与数据脱节”，以下方面基本对齐：

1. 第 6.1 / 6.2 节中的主要 latency 与 FPS 表格，整体与 `experiment_results.json` 一致；
2. 第 5 节中的 ONNX 图节点数、ReLU 数、Add 数、体积变化等，基本与 `onnx_graph_metrics.json`、`variant_graph_metrics.json` 相符；
3. 第 6.3 节 strict suite 中给出的平均值，与 `strict_suite_results.json` 中对应 grouped/aggregated 结果逻辑一致。

因此，报告的大部分主数字是有数据支撑的。

### 6.2 最大的不对齐：报告未正视 `resnet50 bn_folded` 已经数值失效

这是当前“叙事-数据”不对齐最严重的一点。

报告将 `resnet50 bn_folded` 描述为：

- 一个图结构明显收缩但性能反而变慢的优化变体。

而数据却显示它在数值上已经严重失效。也就是说：

- 报告叙事把它当成“合法但效果不好”的优化；
- 数据事实更接近“错误实现或错误导出导致的失败样本”。

这两种解释完全不是一个层级。

### 6.3 `resnet50 fp16` 的验证状态没有与报告结论充分同步

报告在讨论 `fp16` 时，给了它较高关注度，尤其强调其在 strict suite 中的“接近基线”甚至“局部略优”。

但现有数据并不支持把 `resnet50 fp16` 当作“已完成正确性与性能闭环验证”的候选，因为其数值验证状态是失败的。报告如果不显式同步这一点，会让读者自然误以为：

- `fp16` 不仅快，而且正确性也已经验证通过。

这构成一种结论层面的半对齐。

### 6.4 对 strict 单模型异常的叙述力度偏弱

报告确实提到了单模型严格 benchmark 中存在明显异常，并因此转而更倚重 strict suite。这一方向是合理的。

但问题在于，单模型 strict 的异常不是“略有偏差”，而是数量级上的失稳。例如：

- MobileNet baseline 某轮从 `~1.06 ms` 跳到 `3.66 ms`；
- MobileNet fp16 某些轮在 `4.4 ms` 级，另一些轮在 `1.8 ms` 级。

这类现象更应该被视为：

- 实验环境存在重大不稳定因素；

而不只是：

- “长跑条件下受状态影响较大”。

因此，报告对该异常的描述强度低于数据所呈现的严重程度。

## 7. 对现有主要结论的逐条批评

### 7.1 “所有优化都没有超过基线”

这个结论作为工程观察基本成立，但它应当被理解为：

- 在当前基线定义、当前导出链路和当前测试条件下，未观察到这些变体稳定超过现有部署 OM。

而不应直接上升为：

- 所有这些优化方法本身对该平台无效。

因为当前实验设计无法把“优化方法本身”与“重新导出链路差异”完全分开。

### 7.2 “fp16 是唯一值得继续跟踪的方向”

这个结论对 MobileNetV3-Small 尚可勉强成立，因为：

- 它数值验证通过；
- 性能也确实接近基线。

但对 ResNet50 而言，这个结论证据不闭环，因为：

- 数值验证失败；
- 性能优势又非常小。

因此，更精确的说法应是：

- `fp16` 是当前唯一表现出接近基线趋势的方向；
- 但至少在 ResNet50 上，其正确性与稳定性结论尚未闭合。

### 7.3 “节点数减少但没有变快，说明前端简化不等于后端更快”

这句话有一定合理性，但目前拿 `resnet50 bn_folded` 作为最强证据并不可靠，因为这个变体已经数值损坏。

也就是说，这个因果句子的方向可能是对的，但当前最醒目的支撑例子不够干净。

### 7.4 关于硬件瓶颈的归因写得偏强

报告后半部分对 DDR、FixPipe、Cube、MTE2、layout 等问题做了大量分析，这些分析有一定解释力，也与现象大体一致。

但从证据链强度看，现有材料更适合支持：

- “这种解释与现象一致”；
- “这是一个很合理的归因方向”；

而不是过强地写成：

- “已经可以确认最终因果链是如此”。

因为当前直接证据主要还是 benchmark、图统计和已有画像结果，并非专门为这些因果链条设计的控制实验。

## 8. 按严重程度归类的审稿意见

### 8.1 严重问题（Major Issues）

1. **基线不对等**：成熟部署 OM 与重新导出变体直接比较，难以支持“优化本身是否有效”的强结论。
2. **`resnet50 bn_folded` 数值失真仍被纳入性能结论**：这是最严重的数据使用问题。
3. **`resnet50 fp16` 数值验证失败，但仍被赋予较高结论地位**：正确性闭环不完整。
4. **单模型 strict benchmark 出现严重失稳**：说明实验环境中存在强干扰，削弱精细性能比较的可信度。

### 8.2 重要问题（Important Issues）

1. 缺少真正的 `reexport_plain` 中性对照组；
2. 多个优化并非严格单变量实验；
3. strict suite 顺序设计仍可能引入偏差；
4. 极小幅度差异缺乏充分统计支撑；
5. 报告对异常结果的严厉程度低于异常本身的严重程度。

### 8.3 次要问题（Minor Issues）

1. “模型大小”口径混用 ONNX 与 OM；
2. `shape_inferred` / `onnx_shape_inferred` 命名容易混淆；
3. 某些地方使用了“可以确认”“最终归因”等较强措辞，超出了数据本身的证明力度。

## 9. 最终审稿式结论

如果以一个较严格的 critic 视角来评价，这组实验可以给出如下结论：

1. **作为工程观察，报告基本成立**：当前测试到的这些变体确实没有稳定超过现有部署基线。
2. **作为科学比较，实验设计仍不够干净**：现有结果无法将“优化方法本身的效果”与“重新导出链路差异”彻底分离。
3. **作为可复现结论，正确性门槛还未统一执行**：至少 `resnet50 bn_folded` 和 `resnet50 fp16` 的处理方式说明性能结论先于正确性闭环。
4. **作为精细性能分析，环境控制仍不够强**：当前波动水平不足以支撑千分之几、万分之几级别差异的严肃判定。

因此，最稳妥的评价不是“这份报告错了”，而是：

> 这份报告在工程现象总结上是有价值的，但在实验对照纯度、正确性门槛、环境控制和结论措辞上，仍有明显提升空间。它更适合作为阶段性工程分析，而不是作为已经完成严格因果论证的最终实验结论。
